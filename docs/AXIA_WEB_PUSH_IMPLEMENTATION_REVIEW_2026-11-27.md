# Web Push الفعلي — حزمة مراجعة اختبار أندرويد

التاريخ: 27 نوفمبر 2026، القاهرة. الفرع: feat/axia-web-push-20261127؛ Draft PR #58 من main 2703b0cdbc923aba888b588974a5250105236b48. الحالة: تنفيذ مصدر ومراجعة؛ التفعيل وقبول الهاتف لم يحدثا.

## ما الذي نُفّذ؟

مسار فعلي من اشتراك Push في الجهاز إلى سجل اختبار مؤجّل في قاعدة البيانات ثم عامل Node مستقل يوقّع طلب Web Push ويرسله إلى FCM. الخدمة تعمل دون اعتماد على بقاء صفحة AXIA مفتوحة. جهاز الاختبار يختار الاشتراك ويطلب إشعارًا عامًا واحدًا بعد ٩٠ ثانية. الاشتراك ينتهي بعد ١٥ دقيقة بحد أقصى أو انتهاء JWT الحالي، مع إعادة فحص جلسة Auth والعضوية والمكتب وMFA قبل الإرسال.

هذه بداية إثبات الإرسال الخلفي، وليست اكتمال تذكيرات القضايا والمهام الدائمة. الجدولة القانونية، أوقات التذكير الشخصية للمهام ذات التاريخ فقط، وتجديد موافقة الجهاز طويل المدى تحتاج مرحلة تالية. لا تُخترع ساعة انتهاء قانونية ولا تُعدّل مهمة لاختبار الإشعارات. دعم النقل الأول مقيد بـ Chrome/FCM على أندرويد؛ لا يُدّعى قبول آيفون أو جميع المتصفحات.

الإشعار يستخدم نص worker الثابت ورمز AXIA الشفاف، دون اسم عميل أو قضية أو رسالة من جسم الطلب. الضغط يفتح نفس الأصل مع التحقق المعتاد من الدخول، أو يركّز نافذة موجودة دون الانتقال بمحرر غير محفوظ. قبول HTTP 202 أو FCM لا يثبت أن النظام عرض الإشعار.

## حالة main والأجهزة

main فُحص مباشرة عبر GitHub وبقي عند 2703b0c بعد PR #57. أفاد المالك بأن تعديل القائمة ورمز إشعار أندرويد نجحا؛ يسجل ذلك owner-reported PASS. نجاح الإشعار التجريبي الفوري لا يثبت الإرسال عند الإغلاق. لم تُجرّب خدمة الخلفية أو شاشة القفل فعليًا. قبول iPhone وH1 الطبيعي للتجديد/الانتهاء ما زال مفتوحًا.

بيئة التنفيذ المحلية غير متاحة في هذه الجلسة؛ نُشر المصدر عبر GitHub ويُفحص عبر CI في بيئة مؤقتة. قُرئت إرشادات PWA وRoute Handlers من حزمة Next.js 16.3.3 المثبتة داخل CI قبل كتابة مسار Next الجديد. لا يُنسب فحص CI إلى هاتف حقيقي.

### الصلاحيات المقترحة للمراجعة

- axia_push_api_owner: دور NOLOGIN/NOBYPASSRLS يملك جداول ووظائف Push الجديدة فقط، بسياسة داخلية لتشغيل تلك الوظائف. لا عضوية لأي هوية runtime فيه. يحصل على CREATE مؤقتًا لنقل ملكية الكائنات الجديدة ثم تُسحب قبل commit.
- private.axia_push_live: جسر قراءة وحيد مملوك لمشغّل الترحيل المراجع (عادة postgres). يقرأ حقول الصلاحية اللازمة من Auth/العضويات/ضوابط المكتب ويُرجع boolean فقط؛ لا token أو كلمة مرور. EXECUTE لمالك وظائف Push NOLOGIN وحده. يجب مراجعة مالكه ومصدره وصلاحياته قبل أي تطبيق؛ ليس runtime Superuser.
- authenticated: EXECUTE لأربع وظائف جديدة فقط: status/enroll/test/revoke. تستخرج المستخدم والجلسة من JWT الموّثق داخل PostgREST، وتتحقق من عضوية المكتب. صاحب المكتب لا يستطيع الاشتراك نيابة عن موظف أو قراءة اشتراكه.
- axia_push_dispatcher: مجموعة NOLOGIN/NOBYPASSRLS تملك EXECUTE فقط على claim/authorize/finish، دون SELECT عام أو DDL أو وظائف مركز التحكم.
- axia_push_preview_worker: حساب LOGIN منفصل مطلوب لاحقًا بموافقة مستقلة وعضوية المجموعة السابقة فقط. إنشاؤه وكلمة مروره غير موجودين في SQL الحالي؛ لا يُمنح Service Role أو postgres للعامل.

الفحوص تشمل جلسة حية تنتمي للمستخدم، تأكيد الحساب وعدم الحظر، not_after وحدود المدة والخمول وسياسة الجلسة الواحدة وMFA الحالية، وعضوية/حظر العضو وحالة المكتب/انتهائه. تظل مدة الاشتراك اختبارية قصيرة؛ لا يجدد العامل جلسة Auth نيابة عن المستخدم.

نسخة مدد Auth غير السرية يجب قراءتها من مشروع الاختبار نفسه قبل اعتمادها. الأرقام القديمة للمشروع الحالي ليست اعتمادًا لقيم مشروع جديد. attestation تنتهي بعد ٦ ساعات، ويجب إيقاف Push قبل أي تعديل خارجي لسياسات Auth وتجديد المطابقة قبل إعادته؛ لا توجد مزامنة تلقائية لإعدادات الإدارة.

## فحص الموارد المتاحة وحدود القاعدة الجديدة

قراءة قائمة مشاريع حساب Supabase الصحيح أظهرت مشروع AXIA Legal Development القائم بحالة ACTIVE_HEALTHY وPostgreSQL 17.11؛ الاسم Development لا يثبت أنه فارغ أو معزول عن تشغيل AXIA. لم يظهر مشروع Push تجريبي مستقل في الحساب. لم تُقرأ سجلاته أو أسراره أو يُعدّل شيء فيه، والمشروع الآخر غير المتعلق بـAXIA خارج النطاق.

SQL الإثبات يفترض أساس AXIA موجودًا (Auth وprofiles/organization_members/organizations وضوابط المكتب)؛ ليس bootstrap لمشروع Supabase فارغ. قبل أي تطبيق على مورد اختبار جديد يجب تجهيز/مراجعة baseline نظيف متوافق مع الواجهة وRLS وحسابات خيالية، وفحص المخطط الفعلي ونسخة Auth. ملفات التاريخ القديمة تتضمن فروق memberships/organization_members وملفات test_only؛ لا يُعاد تشغيل مجلد migrations التاريخي ولا تُنسخ بيانات/Auth المشروع القائم. هذا عائق تجهيز صريح، وليس قاعدة اختبار منشأة بالفعل.

## خدمة الإرسال المقترحة — لم تُشغّل

[العامل](../workers/push/README.md): Node 22 مستقل بتبعياته المقفلة، يعمل كل خمس ثوانٍ في watch ويعالج حتى ٥٠ claim في الدورة دون إبقاء معاملة قاعدة مفتوحة أثناء الشبكة. لا cron URL عام ولا secret في query. فحص الجاهزية يحتاج نبض العامل خلال آخر ٣٠ ثانية؛ توقفه يمنع اشتراكًا/اختبارًا جديدًا مع إبقاء إبطال الاشتراك متاحًا في الجلسة الصالحة. تشغيل العامل يحتاج مضيفًا دائمًا/حاوية معتمدة؛ Preview على Vercel وحده لا يشغّل عملية دائمة.

هذا الاحتياج التشغيلي قد يكون مدفوعًا. لم تُنشأ خدمة/مشروع أو تُعتمد تكلفة. لا تفعيل على Production. بعد اختيار مكان العامل يجب مراجعة TLS/egress/مراقبة التوقف دون طباعة الأسرار.

النقل الأول يقبل fcm.googleapis.com وHTTPS/443 ومسار FCM المحدد فقط؛ يُرفض أي عنوان آخر، IP خاص أو نتيجة DNS غير عامة. تُثبّت IPv4 المعتمدة في HTTPS Agent ولا توجد إعادة توجيه أو proxy أو fallback DNS/IPv6. مكتبة web-push تتولى VAPID والبروتوكول؛ لا تنفيذ تشفير Web Push يدوي.

إعادة المحاولة ٣ مرات إجمالًا، ٣٠ ثم ١٢٠ ثانية ضمن صلاحية الحدث وبمراعاة Retry-After. 404/410 يلغي الجهاز ويحذف ciphertext؛ 401/403 يوقف بوابة SQL. أخطاء الشبكة قد تكون ذات نتيجة غير مؤكدة؛ لا ضمان exactly-once أو وصول فوري/مضمون. الإلغاء بعد قبول المزود لا يسحب إشعارًا سبق قبوله.

## الاحتفاظ والإيقاف

الإثبات مخصص لقاعدة اختبار معزولة ومراقبة؛ لا يُستخدم كمخزن دائم. يلغي claim الربط منتهي الصلاحية/المفقود ويحذف ciphertext عند عمل العامل؛ الإلغاء الصريح أو 410 يحذفه أيضًا. عند إيقاف العامل لا نفترض تشغيل تنظيف خلفي. بعد التجربة يلزم تنفيذ تنظيف معتمد لسجلات Push الجديدة/التراجع أو التخلص المعتمد من مشروع الاختبار؛ لا حذف حسابات أو بيانات المشروع القائم.

قبل تشغيل دائم يلزم purge محدود ودوري لسجلات terminal/audit بعد ٣٠ يومًا، وضمان حذف ciphertext خلال ٢٤ ساعة من الإبطال حتى والعامل موقوف، وسياسة مفاتيح/نسخ احتياطي مشفرة منفصلة، ومراقبة توقف الخدمة. هذه ليست مكتملة في إثبات الهاتف الأول، ولذلك لا تفعيل Production.

## اختبار أندرويد بعد الاعتماد — خطوة واحدة في كل رسالة

1. نجهّز مشروع الاختبار والعامل بعد مراجعة SQL/الأدوار/الإعدادات والاعتماد، ثم نتحقق من Preview ومصدره. يظل مركز التحكم غير مفعّل ولا ننقل بيانات مكاتب أو Auth من المشروع الحالي.
2. يفتح المالك أصل Preview المحدد على أندرويد، ويثبّت نسخة المراجعة إن لزم. لا يُحذف تطبيق main المثبت؛ الأصلان منفصلان.
3. يدخل المالك بيانات حساب الاختبار وMFA بنفسه إن طُلب. لا يُرسل رموزًا أو ملفات اشتراك إلى المحادثة.
4. يفتح الإشعارات ثم «فحص جاهزية الإرسال في الخلفية». نجاح الجاهزية شرط لظهور زر الاشتراك؛ لا تُطلب موافقة OS تلقائيًا.
5. يضغط «السماح باختبار الخلفية لهذا الجهاز» ويوافق على إذن النظام باختياره. تظهر مدة الاشتراك الاختباري.
6. يضغط «اختبار بعد ٩٠ ثانية». نقرأ وقت الإرسال الذي أعاده الخادم، ثم نطلب إغلاق AXIA إغلاقًا عاديًا وقفل الشاشة مع بقاء الإنترنت. لا نستخدم Force Stop أو نغيّر حماية/بطارية الهاتف لهذا الاختبار.
7. يسجل المالك هل وصل الإشعار على الشاشة المقفولة ووقته التقريبي ورمز AXIA. لا يُعد نجاح الطلب في الواجهة PASS للوصول.
8. يضغط الإشعار: يفتح نفس Preview/مساحة العمل أو يطلب الدخول المعتاد؛ لا تجاوز للمصادقة. نجرّب إعادة الإرسال/الإلغاء فقط ضمن جهاز الاختبار وحدود الطلبات وبإذن صريح.
9. نلغي اشتراك الاختبار، وننفذ الإيقاف والتنظيف المعتمدين. نسجل نتائج الهاتف منفصلة عن CI.

الإنترنت/Eذن النظام/Focus/قيود OS قد تؤثر في العرض؛ إغلاق التطبيق العادي يختلف عن إيقاف خدمة المتصفح قسريًا أو إطفاء الجهاز. يظل نجاح التسليم الفعلي بحاجة لتجربة المالك.
