# مواصفات حزمة السيرفر المحلي P2 — للمراجعة

التاريخ: 25 نوفمبر 2026، القاهرة. الحالة: `READY_FOR_SCOPE`، تصميم فقط. مرجع التطبيق المختبر: PR #54، المصدر `cd5d1189d7d3e2abed77b8423ec8a294735c742d`، المبني على PR #53. لا توجد حزمة تشغيل محلي أو قاعدة محلية جديدة في هذا التغيير.

## النتيجة المقصودة

يفتح الكمبيوتر واللاب توب وأندرويد وآيفون نفس تطبيق AXIA من متصفح أو PWA، ويتصلون بسيرفر المكتب عبر الشبكة الداخلية. عند انقطاع الإنترنت الخارجي تستمر وظائف المكتب المحلية بعد تجهيز الخدمة، ما دام السيرفر والشبكة الداخلية يعملان. انقطاع شبكة المكتب نفسها يحتاج وضع الجهاز دون اتصال P3/P4، وهو غير منفذ بعد.

لكل مكتب مصدر معتمد واحد: السحابة أو السيرفر المحلي. هذه الحزمة المقترحة تبدأ بمكتب وهمي مستقل؛ لا تنقل مكاتب السحابة أو حساباتها أو ملفاتها. لا توجد كتابة مزدوجة بين السحابة والمحلي. نقل مكتب حقيقي مستقبلًا يحتاج قائمة نقل واستعادة وهوية وتوقف كتابة معتمدة منفصلة.

## 1. المكونات وحدود الوصول

| المكوّن المقترح | الوظيفة | الوصول والحفظ |
| --- | --- | --- |
| بوابة HTTPS، مرشح أولي Caddy | شهادات موثوقة، حدود الطلب، توجيه التطبيق والـAPI | منفذ 443 فقط لشبكة المكتب المعتمدة؛ الاسم والشهادة يحتاجان اختيارًا |
| تطبيق AXIA / Next.js | نفس واجهة وصلاحيات المرشح المعتمد | حاوية Node 22 مبنية من مصدر محدد؛ المنفذ الداخلي غير مكشوف للمستخدمين |
| Supabase ذاتي الاستضافة | Auth وPostgREST وStorage والخدمات التي تثبت الحاجة إليها | إصدار Compose متوافق وصور مثبتة بالـdigest قبل البناء؛ لا تتبع `latest` تلقائيًا |
| PostgreSQL وبيانات Storage | السجلات والمرفقات الأصلية | مجلدات دائمة منفصلة عن صورة التطبيق؛ Postgres غير متاح لأجهزة العملاء |
| الإدارة والنسخ الاحتياطي | صحة الخدمة، التحديث، النسخ والاستعادة | وصول مشغل محدود؛ Studio ومنافذ الإدارة ليست ضمن واجهة الموظفين |

استخدام Supabase CLI للتطوير لا يجعله حزمة تشغيل مكتب معتمدة. تبدأ نسخة P2 التجريبية بإعداد Docker ذاتي الاستضافة موثق، لا بكشف بيئة التطوير على الشبكة. لا نحذف خدمة من Compose لمجرد تقليل الذاكرة قبل تتبع اعتماد التطبيق عليها.

## 2. الجهاز والتخزين والتكلفة

معلومات المورّد التي تمت مراجعتها: الحد الأدنى لحزمة Supabase الكاملة 4GB RAM، نواتان و40GB SSD؛ الموصى به 8GB+ و4 أنوية+ و80GB+ SSD [S1]. هذه ليست قياسات أداء AXIA.

**اقتراح AXIA الأولي، يحتاج تجربة حمل:** Linux مدعوم 64-bit على جهاز مخصص أو VM، 4 أنوية و16GB RAM وSSD بسعة 256GB كبداية، مع مصدر كهرباء احتياطي ووسيط نسخ منفصل. لا يُشترى جهاز اعتمادًا على هذا الرقم وحده؛ حجم المرفقات وعدد المستخدمين والنسخ يحددون السعة الفعلية. إذا كان الجهاز المتاح 4GB ويُستخدم للمتصفح والعمل اليومي، نستعمله كعميل PWA ونراجع خادمًا منفصلًا.

ميزانية القرص تشمل النظام والصور وقاعدة البيانات والملفات والسجلات ومساحة التحديث والاستعادة، مع احتياطي تشغيلي مقترح 30%. تقدير نسخة أولى يحتاج قياس نمو البيانات والمرفقات. نسخة احتياطية على نفس القرص لا تحمي من تلفه. تكلفة الجهاز والكهرباء والدومين والتخزين والصيانة تُعرض بعد حصر الموجود؛ لا توجد مشتريات أو اشتراكات أو حجز بنية الآن.

## 3. الشبكة وHTTPS

- اسمان مقترحان تحت نطاق يملكه المكتب: `https://axia.<owned-domain>` للتطبيق و`https://api.axia.<owned-domain>` للـAPI. هذه أسماء رمزية غير مخصصة، وليست روابط تنفيذ. DNS الداخلي يوجههما لعنوان ثابت للسيرفر.
- تُراجع شهادة موثوقة على Windows/Android/iOS. خيار شهادة عامة مع DNS challenge يحتاج نطاقًا وصلاحية DNS وخطة تجديد؛ لا يعني فتح قاعدة البيانات أو واجهة الإدارة للإنترنت. تجديد الشهادة وتنزيل التحديثات يحتاجان نافذة اتصال مخططة. إن اختيرت CA داخلية، تعرض خطوات الثقة على الأجهزة واعتمادها قبل التنفيذ. لا نطلب تجاوز تحذيرات المتصفح.
- لا نفترض أن عنوان LAN عبر HTTP يعطي مميزات PWA. استثناء localhost يخص الجهاز نفسه ولا يحل وصول الموبايل إلى كمبيوتر المكتب.
- توثّق لاحقًا شبكة العملاء وعنوان السيرفر وقواعد الجدار الناري وVPN إن طُلب وصول خارجي. لا يُفتح منفذ أو DNS أو ملف hosts في هذه المرحلة.
- يلزم وقت صحيح للسيرفر والأجهزة: NTP محلي موثوق/خطة تصحيح الساعة، مع تخزين الطوابع في UTC وعرض القاهرة. هذا مهم للجلسات وTOTP والشهادات.

## 4. إعدادات التطبيق والمصادقة المعروضة قبل التطبيق

جميع القيم التالية **مقترحات للبيئة المحلية الجديدة فقط**. لا تتغير إعدادات Supabase أو Vercel الحالية.

| البند | المقترح | ما يحتاج مراجعة قبل التنفيذ |
| --- | --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | أصل الـAPI المحلي المختار | تثبيت الاسم وHTTPS واختبار وصول المتصفح والخادم إليه |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | المفتاح العام للنسخة المحلية الجديدة | توافق نسخة العميل والخدمات؛ لا نسخ لمفاتيح السحابة |
| إعدادات عامة تبدأ `NEXT_PUBLIC_` | تُثبت وقت بناء النسخة المحلية | Next.js يضمّنها أثناء البناء؛ تغيير env وقت تشغيل الصورة الحالية وحده لا يكفي [R1] |
| `SITE_URL` / `GOTRUE_SITE_URL` | أصل تطبيق المكتب | تأكيد أسماء المتغيرات في إصدار Compose المثبت |
| `API_EXTERNAL_URL` | أصل API المحلي مع `/auth/v1` وفق الإصدار الحالي | منع تكرار المسار؛ اختبار مسارات العودة والـissuer [S4] |
| قائمة redirect | المسارات اللازمة فقط تحت الأصل المعتمد، بلا wildcard عام | قائمة دقيقة لمسارات التطبيق الموجودة واختبارات رفض الأصل الأجنبي |
| JWT وحدود الجلسة | مقترح أولي access token لمدة 3600 ثانية؛ حد الخمول والحد المطلق لم يُعتمدا | عرض القيم المحددة وآلية التجديد/الإنهاء قبل ضبط Auth؛ لا نقل افتراض unlimited إلى عقد عميل |
| الحسابات | مستخدمون وهميون محليون بأقل صلاحية؛ لا public signup في الطيار | عدد الحسابات والأدوار وتهيئة مالك المكتب ووسيلة استعادة الدخول تحتاج قائمة معتمدة |
| البريد وMFA | لا SMTP خارجي ولا نسخ لكلمات مرور أو TOTP من السحابة | بريد اختبار محلي معزول عند الحاجة؛ دخول/MFA خاص بالمالك. لا تعطيل لحماية مطلوبة لاجتياز الاختبار |
| platform / control center / staff registration | مفاتيح التفعيل مغلقة افتراضيًا | أي تفعيل لاحق وقيم Origin له قرار مستقل؛ مالك المكتب لا يصبح مالك المنصة |
| الأسرار المحلية الجديدة | يولدها المشغل داخل الخادم بعد اعتماد النطاق | تخزين محمي ونسخة استرداد مشفرة وتدوير؛ لا أسرار في Git أو PWA أو محادثة |

يجب أن تفشل حزمة التشغيل المحلية عند غياب إعداد حقيقي، بدل عرض قاعدة وهمية كأنها بيانات مكتب. المصدر الحالي يحتوي fallback إلى `createMockSupabaseServerClient()` عند غياب الإعداد؛ P2 يحتاج فحص بدء تشغيل/حزمة واضحًا واختباره قبل اعتماده، دون تغيير مصدر PWA في هذه الوثيقة [R2].

## 5. قاعدة البيانات: المطلوب قبل أي SQL

لا يوجد ترحيل SQL جديد هنا. لا يجوز إعادة تشغيل مجلد المهاجرات كله على Supabase الرئيسي أو اعتباره مثبتًا محليًا جاهزًا.

المراجعة المصدرية وجدت أن `20260919091000_rajih_foundation.sql` ينشئ `memberships` و`membership_role`، بينما أجزاء لاحقة والاختبارات تستعمل `organization_members` و`app_role`. كذلك توجد ملفات مسماة `test_only_*`. هذه ملاحظة عن تاريخ المصدر، لا حكم بأن القاعدة المستضافة الحالية معطلة [R3].

قبل بناء P2-A يعرض ملف تأسيس نظيف لقاعدة **فارغة محلية معزولة**، يحتوي ترتيب الاعتماد، الجداول والأنواع والدوال والمشغلات والـRLS والـGRANTs وامتداداتها المطلوبة. تُراجع كل قطعة تاريخية وتجريبية، وتوثّق بصمات SQL وترتيب تطبيقه. وجود RLS لا يغني عن مراجعة امتيازات الوصول إلى الـAPI [S6]. لا يتضمن التأسيس صفوفًا أو هويات حقيقية، ولا seed يمنح صلاحية منصة تلقائيًا.

اختبارات P2 المقترحة تشمل JWT حقيقيًا من Auth المحلي، عزل مكتبين وهميين، ACL القضية، حدود المالية، انتهاء/revocation الجلسة، رفض حساب/أصل من السحابة، وإثبات غلق مسارات الإدارة. قواعد CI المؤقتة الحالية دليل انحدار مفيد، وليست بديلًا عن قبول مجموعة الخدمات المحلية الحقيقية.

Postgres 17 مرشح لقاعدة محلية فارغة؛ نسخة الصورة والامتدادات تثبت بعد تجربة التوافق. لا نركب مجلد PG15 على PG17 ولا ننقل مجلدات بيانات بين إصدارات رئيسية مباشرة [S5]. لا يتغير إصدار القاعدة السحابية.

## 6. الإنترنت الخارجي والمرفقات

عند قطع WAN مع بقاء LAN: يجب أن يعمل الدخول المحلي والقراءة والوظائف المحلية التي تُعتمد ضمن قائمة الطيار. تُحزم الخطوط والأيقونات والواجهات المطلوبة محليًا، وتُفحص الطلبات الخارجة عمليًا. خدمات راجح الخارجية والخرائط والبريد الخارجي وتجديد الشهادة وتنزيل صور جديدة لا تُعتبر وظائف تعمل دون إنترنت. يُعرض تعذرها بوضوح، ولا تُرسل عملياتها تلقائيًا لاحقًا.

المرفقات تُخزن عبر Storage المحلي مع بياناتها الوصفية والـhash والصلاحيات. لا تستعمل روابط Storage سحابية خفية. الموبايل خارج LAN لا يصل إلى السيرفر حتى يُعتمد وصول خارجي آمن؛ تثبيت PWA وحده لا يغير ذلك.

## 7. النسخ والاستعادة والتحديث

اقتراح للمراجعة: نسخة يومية مشفرة ونسخة قبل كل تحديث، و7 يومية +4 أسبوعية، على وسيط مستقل مع مفتاح استرداد منفصل. هدف أولي RPO حتى 24 ساعة وRTO حتى 4 ساعات **غير مثبت وغير تعاقدي**؛ يُقاس في اختبار استعادة ببيانات الطيار قبل اعتماده. لا جداول مجدولة أو exports أو أجهزة نسخ جديدة في هذه المرحلة.

تحتوي حزمة الاستعادة المعتمدة على نسخة متسقة من DB + المرفقات الفعلية + schema/manifest/hash وقائمة الإصدارات وإعدادات غير سرية. البيانات الوصفية لـStorage وحدها ليست بايتات الملفات [S3]. النسخ الكامل لخادم Auth يتضمن مواد هوية حساسة؛ يُحصر في نسخ تشغيل مشفرة ومراجعة صلاحية المشغل، ولا يدخل snapshot متصفح أو Git أو سجل دعم. مفاتيح التشغيل/الاسترداد لها مسار حفظ محمي منفصل.

إجراء الاستعادة: هدف محلي فارغ ومعزول، تحقق من hashes والعلاقات والصلاحيات والمرفقات، اختبار الدخول وإبطال الجلسات وفق خطة Auth المعتمدة، ثم اختبار تعارض/فقد ملف/كلمة استرداد غير صحيحة. لا يكتب الاختبار على المصدر ولا يعيد جلسات السحابة.

التحديث عبر artifact موثق وبصمات وصور مثبتة، ونسخة احتياطية والتحقق من الصحة. العودة لصورة تطبيق قديمة لا تُرجع schema تلقائيًا؛ التوافق أو الاستعادة يُختبران قبل التحديث. لا أوامر reset أو حذف volumes في مسار تشغيل المكتب العادي.

## 8. ملفات P2-A المطلوبة لاحقًا

1. manifest إصدار يثبت SHA التطبيق وCompose وصور الخدمات ومتطلبات النظام.
2. Dockerfile/Compose وreverse-proxy template مدققة، وملف إعدادات نموذجي بلا أسرار؛ لا حزمة runnable في هذا المستند.
3. فحص preflight: الإعداد الحقيقي، الموارد والمساحة والوقت وDNS/HTTPS/صلاحيات المجلدات؛ لا تثبيت صامت أو حذف بيانات عند الفشل.
4. baseline SQL وقائمة fixture معروضة للاعتماد قبل تطبيق DB/Auth.
5. دليل تشغيل/إيقاف وصحة ونسخ/استعادة وتحديث وتراجع، مع redaction للسجلات وhashes للأدلة.

## 9. بوابة القبول وما يحتاج المالك

لا يبدأ تشغيل خادم أو تعديل قاعدة/مصادقة اعتمادًا على هذه الوثيقة وحدها. الخطوة التالية في P2 هي إقرار نطاق طيار معزول وقائمة تغييرات ملموسة. يلزم لاحقًا تحديد الجهاز المتاح وموارد CPU/RAM/SSD، عدد المستخدمين وحجم الملفات، نطاق/طريقة ثقة HTTPS، مسؤول التشغيل وموقع النسخ ومفتاح الاسترداد، وطريقة الحسابات والبريد وحدود الجلسة. لا نحتاج كلمات مرور أو رموز MFA في المحادثة.

قبول P2 يحتاج: تشغيل بعد reboot، استمرار العمل المحلي عند قطع WAN فقط، منع الوصول عند قطع LAN مع توضيح الحالة، تثبيت PWA على الأجهزة الفعلية، عزل المكتب/القضية والمالية، جلسات محلية حقيقية، استعادة إلى جهاز/هدف آخر، وتحديث/تراجع موثق. كل نتيجة تظل مفتوحة حتى توجد أدلة فعلية.
