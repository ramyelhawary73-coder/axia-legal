# AXIA — حزمة مؤقت Cloudflare المجاني للمراجعة

الحالة: **كود واختبارات فقط؛ لم تُنشأ موارد Cloudflare أو تُنقل مفاتيح أو يُطبق SQL جديد.**
الفرع: `feat/axia-push-edge-free-20261127` / Draft PR #59. لا دمج main أو Production. الإرسال ومركز التحكم مغلقان وT0 لم يبدأ.

## السبب والحدود

أُزيل pg_net غير المستخدم بعد فشل تقييد صلاحيات الكائنات المُدارة. المصدر البديل يضع المؤقت فقط في Cloudflare Workers Free، ويبقي اتصال القاعدة والتشفير وVAPID وبيانات الأجهزة والمُرسل داخل Supabase الحالي. العزل منطقي للحساب والمكتب المعتمدين في مشروع AXIA المشترك؛ ليس قاعدة مستقلة.

## تغيير SQL بالتحديد

1. معاملة واحدة تقفل جدولي إعدادات Push فقط، وتفشل إذا كانت بوابة مفتوحة أو نافذة باقية أو pg_net مثبتًا أو job قديمًا موجودًا. لا توقف job مشتركًا أو تحذف إضافة بنفسها.
2. `private.axia_push_edge_begin(bigint)` يحتفظ بمالكه API owner وصلاحياته الحالية؛ يتحقق من عدم انكشافه لـanon/authenticated ومن EXECUTE للـdispatcher. لا وصول مباشر للجدول أو Vault من العامل أو المؤقت.
3. يقرأ الساعة **بعد** قفل صف التحكم؛ يتحقق من الحساب/المكتب المحددين والنافذة ≤30 دقيقة وبوابتي SQL. يقبل slot توقيع للدقيقة الحالية/السابقة فقط، ويحجز حسب دقيقة قاعدة البيانات الحالية؛ لا يمكن لطلبي توقيع لدقيقتين مختلفتين دخول نفس دقيقة التنفيذ.
4. حجز الميزانية ومنع الإعادة في UPDATE ذري واحد، بحد أقصى 200 قبول شهريًا UTC. تغيير الشهر يعيد الميزانية عند القبول فقط، ويحفظ منع تكرار الدقيقة. الحجز يثبت قبل I/O؛ الفشل أو عدم وجود مهمة بعد القبول يستهلك وحدة أيضًا.
5. `private.axia_push_edge_tick()` القديم يصبح no-op يعيد NULL دون net أو قراءة Vault؛ يحتفظ بملكيته وACL. لا تركيب Cron بديل داخل قاعدة البيانات.

الحد 200 يحكم **القبول الموقّع داخل SQL**، ولا يمنع احتساب طلبات HTTP المرفوضة أو فحوص الصحة لدى Supabase. lock الانتظار أعيد اختباره حتى انتهت النافذة، ورفض الطلب دون استهلاك. تتوقف صلاحية الإرسال الحية عند SQL cutoff؛ قبول المزود قبل القطع قد ينتج وصولًا لاحقًا ضمن TTL.

## التكلفة والحصة

الوثائق الرسمية المفتوحة في 27 نوفمبر: Workers Free يتيح 100,000 طلب/يوم و5 Cron Triggers و100 Worker للحساب و10ms CPU لكل invocation. المؤقت مرة/دقيقة = 1,440 حدثًا/يوم إن بقي Cron مسجلًا، حتى عندما تمنع الأعلام الطلبات إلى Edge؛ نافذة إرسال 30 دقيقة لا تلغي Cron تلقائيًا. عدم ترقيته يحافظ على هدف صفر تكلفة إضافية؛ تجاوز الحدود قد يوقف التنفيذ.

**حصة الحساب الفعلية غير مؤكدة**: المتصفح فتح Sign in to Cloudflare؛ لم تتم مصادقة أو إنشاء حساب أو قبول شروط أو فحص دفع. يلزم تسجيل دخول المالك وقراءة Workers plan/الاستخدام/عدد Cron والموارد الموجودة قبل اعتماد إنشاء مورد. Supabase الحالي Free من القراءة السابقة؛ حصة Edge 500,000 للدورة مشتركة وقد تأخرت لوحة الاستخدام، ولا نكرر رقم 0 باعتباره الاستهلاك الحالي بعد فحوص الإقلاع.

لا يثبت الاختبار المحلي أن CPU على Cloudflare المستضاف أقل من 10ms، أو اتصال المُرسل بقاعدة Supabase، أو استقبال الهاتف. هذه بوابات مستقلة قبل T0. انتشار إضافة/حذف/تعديل Cron قد يستغرق 15 دقيقة؛ لا نعتمد على حذف Cron كإغلاق فوري ولا نبدأ الـ30 دقيقة أثناء انتظار الانتشار.

## نتائج الفحص

- 7 اختبارات Node للمؤقت نجحت؛ التوقيع تحقق بالمُصادق نفسه المستخدم في Edge، ومنها رفض توقيع مختلف/منتهي، انقضاء النافذة أثناء التشفير، وعدم وجود أسرار/مستلم في الطلب.
- Wrangler dry-run نجح محليًا. تشغيل الحزمة في workerd كشف أن `redirect:error` غير مدعوم؛ صحح إلى `manual`، واختبار workerd أثبت عدم اتباع Location أو تكرار الطلب. نجحت إثباتات التشغيل الخمسة.
- 8 اختبارات Deno نجحت، منها 21 فحص PostgreSQL 17: الحصر، ACL، رفض ترحيل حي/legacy Cron، منع تكرار دقيقة، cap والشهر، عميلان محدودان متزامنان، انتهاء النافذة أثناء انتظار القفل، والمسار Web Crypto → Edge → SQL → مُرسل stub. التراجع حافظ على المستخدمين والجلسات والعضويات في fixture.
- إعادة قراءة المشروع المستضاف فقط: صفر Cron/devices/outbox، بوابات SQL false، البداية والنهاية NULL، وpg_net غير مثبت. لم يطبق ملف SQL الجديد أو يتغير مُرسل Edge المستضاف.
- نتيجة CI وPreview لهذا التغيير تُقرأ من commit بعد رفعه؛ نجاح المصدر السابق لا يُعد نجاحًا تلقائيًا للمصدر الجديد. لا قبول هاتف أو Cloudflare مستضاف حتى الآن.

## تسلسل التنفيذ بعد المراجعة — ليس تفويضًا

1. المالك يسجل الدخول إلى Cloudflare بنفسه، ثم قراءة الخطة والاستخدام والحصة دون تعديل. إن لم تتوفر حصة مجانية، نتوقف دون ترقية أو حذف موارد حالية.
2. عرض المصدر المحدد وCI/Preview وSQL ووجهة HMAC للموافقة. تحتاج إنشاء Worker ونقل HMAC وتطبيق SQL موافقة تنفيذ منفصلة.
3. بعد هذه الموافقة فقط: تطبيق SQL والبوابات مغلقة، ثم نشر Worker مغلقًا وإضافة HMAC باسمه المحدد، بلا Cron ونافذة. فحص CPU/التوافق المستضاف والاتصال بقاعدة Supabase دون إرسال، بخطة اختبار مغلقة معروضة أولًا؛ فحص boot المغلق الحالي لا يثبت اتصال القاعدة.
4. قبل تشغيل مستقل: إعادة قراءة Auth غير السري، جاهزية الدخول/MFA ورضا الجهاز، وفحص انتشار Cron والأعلام مغلقة. عند إعلان المالك الجاهزية فقط تُضبط نافذة SQL/Worker المتطابقة 30 دقيقة ويبدأ اختبار Android إغلاق عادي وشاشة مقفولة وإنترنت متصل. رضا الجهاز ≤15 دقيقة/JWT، وليس 30 دقيقة تلقائيًا.
5. الإغلاق: أعلام Worker/Edge/app/SQL إلى 0 مع إيقاف Cron المسمى لاحقًا، وعدم حذف سجلات Push أو بيانات الأعمال. إذا أُلغي البديل، يبقى مغلقًا ولا يُعاد pg_net؛ التراجع الكامل لحزمة Push معروض منفصلًا ويحتاج قرار احتفاظ بالسجلات والمفاتيح/LOGIN.

**أمر الخطوة التالية:** «سأدخل إلى Cloudflare بنفسي؛ اقرأ الخطة والحصة والموارد فقط، ثم اعرض حزمة اعتماد SQL ومؤقت PR #59 ووجهة مفتاح HMAC بالقيم النهائية. لا تنشئ موارد أو تنقل مفاتيح أو تطبّق SQL أو تفعّل إرسالًا حتى أعتمد التنفيذ منفصلًا. لا تدمج main أو تنشر Production.»
